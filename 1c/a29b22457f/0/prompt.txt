# Run-log schema: `outcome_verdict`, `prep_verdict`, `responder_runs[]` present (null) on every drain

## What

Three new fields are present on every run-log entry: `outcome_verdict` (null), `prep_verdict` (null), `responder_runs` (empty array). Their shapes are documented in-code.

## Why

These are the write targets for the Outcome Verifier (M2), PR Preparer (M3), and PR Responder (M4). They must exist before any role can write to them, and must be present on all drains so the grader can inspect them uniformly.

## Assumptions

* `outcome_verdict` shape: `{result, findings[], invoked_at}` or `null`.
* `prep_verdict` shape: `{result, route, reasoning}` or `null`.
* `responder_runs` is an array of `{comment_ids[], invoked_at, result}` objects, empty by default.

## Key Risks

* Introducing new fields on existing schema may break deserialisation in run-log readers if they use strict parsing; a forward-compatible parse strategy must be confirmed.
* The field shapes must be stable before M2/M3/M4 consume them — any shape change after those milestones begin is expensive.

## Definition of Done

* Every drain (verify or default) produces a run-log entry that includes `outcome_verdict: null`, `prep_verdict: null`, `responder_runs: []`.
* The field shapes match the spec in `docs/initiative-multi-agent-collaboration.md`.
* Existing run-log readers produce no errors on entries with the new fields.
