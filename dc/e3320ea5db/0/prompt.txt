# Record PR links in the run-log and Linear, and document the new default

**Depends on:** [ABA-302](https://linear.app/ababushkin/issue/ABA-302/assemble-one-stacked-pr-per-repo-and-flag-what-needs-review).

## What

The run-log records each PR (URL, number, `review_high`, parent branch), the orchestrator posts the PR link back to the Linear issue, and the docs describe stacking-as-default with the override.

## Why

The operator and any future session need to find a drain's PRs and understand the workflow without re-reading source. Memory lives in artefacts, not in agents.

## How (mechanical)

* Add `pr_url`, `pr_number`, `review_high`, and `parent_branch` to `runlog.append_entry` as additive keyword params, and to the entry dict; update the schema docstring (`drain_cycle/runlog.py:16` and `:147`). These are additive — `grade.py` reads only `cycle_id` / `final_linear_state` / `exit_code`, so old logs grade unchanged.
* Add `linear.add_comment(issue_id, body)` (GraphQL `commentCreate`); the orchestrator posts the PR link + review:high status after submit.
* Update `AGENTS.md` (the completion sequence now branches by mode), `README.md`, and add `docs/design-decisions.md §13` (mirror §12's prose: decision, alternatives considered, consequences).

## Acceptance criteria

- [ ] A run-log round-trips the new fields, and `grade.py` grades pre-existing run-logs unchanged. (test)
- [ ] After a live drain, each issue carries a Linear comment with its PR link.
- [ ] `AGENTS.md`, `README.md`, and `docs/design-decisions.md §13` describe stacking-as-default and the override.
- [ ] `pytest` passes.
