# Worker session invokes `/shape:task` before implementation on `verify`-flow tickets

## What

The drain-cycle worker session for `verify`-flow tickets invokes `/shape:task` as the first step before any implementation begins, and includes the Task Shaper output in the implementer's prompt context.

## Why

Without this wiring, the Task Shaper skill exists but is never invoked by the worker — the role doesn't participate in the drain flow and the AC enrichment never reaches the implementer.

## Assumptions

* The worker session can prepend a shaping step before handing off to the implementer.
* The Task Shaper output format is stable (the `/shape:task` skill issue is done first).
* Non-verify-flow drains are unchanged.
* On a §14 resume, the worker checks the Linear issue body for an existing Task Shaper output block; if found, it uses that block as context and skips re-invoking `/shape:task`. This is the mechanism that makes [ABA-326](https://linear.app/ababushkin/issue/ABA-326/task-shaper-output-written-to-linear-issue-body-for-durable-context)'s dual-write the durable artefact. See design decision §17.

## Key Risks

* The shaping step adds latency and token cost per ticket; if material, `limits.yml` overrides may be needed (addressed in M5).
* If `/shape:task` surfaces irresolvable AC gaps, the skill flags them and returns (it does not hang or halt the worker). The worker passes the flagged gaps through to the implementer's context — the implementer proceeds with explicit awareness of the gaps rather than silently.

## Definition of Done

* A `verify`-labelled drain invokes `/shape:task` before the implementer begins.
* The implementer's prompt context includes the Task Shaper output.
* A non-verify-flow drain does not invoke `/shape:task`.
* The run-log entry includes evidence that the shaping step ran.
* A resumed verify-flow drain (§14) skips the `/shape:task` invocation if a Task Shaper output block already exists in the Linear issue body, and uses the existing block as implementer context.
